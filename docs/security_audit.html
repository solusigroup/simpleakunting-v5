Multi-Tenancy & Isolasi Data

Pemisahan data tingkat tinggi antar-perusahaan penyewa (Tenant)

🏢 1.1 Isolasi Fisik Database Perusahaan

Sistem menghindari penggunaan single database multi-tenant (yang rentan terhadap kebocoran data akibat hilangnya clause WHERE di baris kode). Sebaliknya, diimplementasikan arsitektur database terisolasi menggunakan Stancl/Tenancy.

✓
Keamanan Terjamin: Saat subdomain diakses, middleware akan mengganti koneksi database default secara dinamis ke database tenant spesifik (`dbv5_{tenant}`). Tidak ada query SQL yang dapat melintasi database tenant lain.
Lihat Konfigurasi Multi-Tenancy (config/tenancy.php) ▼ 
<?php
declare(strict_types=1);

use Stancl\Tenancy\Database\Models\Domain;
use App\Models\Tenant;

return [
    'tenant_model' => Tenant::class,
    'id_generator' => null, // Kustom tenant ID (contoh: perusahaanA)

    'bootstrappers' => [
        Stancl\Tenancy\Bootstrappers\DatabaseTenancyBootstrapper::class,
        Stancl\Tenancy\Bootstrappers\CacheTenancyBootstrapper::class,
        Stancl\Tenancy\Bootstrappers\FilesystemTenancyBootstrapper::class,
        Stancl\Tenancy\Bootstrappers\QueueTenancyBootstrapper::class,
    ],
    // ...
];

🚫 1.2 Pencegahan Akses Lintas Domain & Blokir Tenant Nonaktif

Untuk memastikan tenant tidak dapat diakses secara ilegal dan mematuhi lisensi penagihan:

  • PreventAccessFromCentralDomains: Middleware ini mencegah domain pusat (landing page) mengakses route yang didedikasikan untuk bisnis tenant.
  • CheckTenantActive Middleware: Membaca status `is_active` pada model tenant saat inisialisasi request. Jika bernilai false, sistem otomatis memotong proses alur request dan membuang respons 403 Forbidden dengan alasan pemblokiran yang jelas.
Kode Middleware CheckTenantActive.php ▼ 
<?php
namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class CheckTenantActive
{
    public function handle(Request $request, Closure $next): Response
    {
        $tenant = tenant();

        if ($tenant) {
            if (isset($tenant->is_active) && $tenant->is_active == false) {
                abort(403, "Akses Diblokir: Perusahaan '{$tenant->nama_perusahaan}' saat ini berstatus NONAKTIF. Silakan hubungi Administrator pusat.");
            }
        }

        return $next($request);
    }
}

Autentikasi & RBAC (Role-Based Access Control)

Verifikasi identitas pengguna dan manajemen hak akses terperinci

🔑 2.1 Enkripsi Kredensial Hashing

Aplikasi menggunakan algoritma enkripsi satu arah **Bcrypt** dengan default 12 putaran putaran hashing (work factor) untuk mengenkripsi password sebelum disimpan ke database, mencegah kebocoran password mentah jika database dicuri.

// Metode verifikasi login di AuthController
if ($user && Hash::check($credentials['password'], $user->password_hash)) {
    Auth::login($user);
    // ...
}

🛡️ 2.2 Role & Permission Middleware

Hak akses dibagi menjadi 5 tingkatan (Superuser, Admin, Manajer, Staff, Kasir). Validasi dilakukan di tingkat route grup menggunakan middleware:

  • RoleMiddleware: Memastikan pengguna memiliki setidaknya salah satu role yang diperlukan. Menariknya, role superuser diset untuk mem-bypass semua verifikasi role.
  • PermissionMiddleware: Menyediakan pengecekan granular di level fitur (seperti pembatasan izin pembuatan, pengeditan, atau penghapusan data jurnal).
Kode RoleMiddleware.php ▼ 
<?php
namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class RoleMiddleware
{
    public function handle(Request $request, Closure $next, string ...$roles): Response
    {
        $user = $request->user();

        if (!$user) {
            $isCentralDomain = in_array($request->getHost(), config('tenancy.central_domains', []));
            return redirect()->route($isCentralDomain ? 'central.login' : 'login');
        }

        // Superuser bypass verifikasi
        if ($user->isSuperuser()) {
            return $next($request);
        }

        // Validasi role
        if (!empty($roles) && !$user->hasRole($roles)) {
            abort(403, 'Akses ditolak. Anda tidak memiliki izin untuk mengakses halaman ini.');
        }

        return $next($request);
    }
}

Integritas Data Transaksi Finansial

Validasi logika bisnis akuntansi agar data konsisten dan tidak dapat dimanipulasi

🏢 3.1 Isolasi Data Tingkat Cabang (Multi-Branch Scope)

Untuk perusahaan yang memiliki banyak cabang, isolasi data transaksi wajib dilakukan di level database agar user cabang A tidak dapat mengintip atau menyunting transaksi cabang B.

Ini diselesaikan secara elegan menggunakan global scope CabangScope yang disematkan ke trait HasCabang pada setiap model akuntansi:

// Implementasi filter otomatis di CabangScope.php
public function apply(Builder $builder, Model $model)
{
    $user = auth()->user();
    if (!$user) return;

    $table = $model->getTable();

    if ($user->hasRole(['superuser', 'admin'])) {
        // Admin pusat dapat melihat cabang terpilih berdasarkan filter session aktif
        $activeCabang = session('active_cabang');
        if ($activeCabang) {
            $builder->where($table . '.id_cabang', $activeCabang);
        }
    } else {
        // Staff/Manajer cabang dikunci hanya untuk melihat cabang miliknya sendiri
        $userCabang = $user->id_cabang;
        if ($userCabang) {
            $builder->where($table . '.id_cabang', $userCabang);
        }
    }
}

🔒 3.2 Proteksi Transaksi Periode Tutup Buku

Saat laporan keuangan bulanan disepakati dan ditutup, periode tersebut dikunci (Tutup Buku). Untuk mencegah perubahan data masa lalu secara ilegal, disematkan trait [CheckClosedPeriod](file:///d:/PROJECT_HERD/simpleakunting-v5/app/Traits/CheckClosedPeriod.php) di setiap mutasi jurnal:

protected function validatePeriodOpen(string $tanggal): void
{
    $date = Carbon::parse($tanggal);
    $bulan = $date->month;
    $tahun = $date->year;

    // Cek apakah bulan/tahun tersebut berstatus 'tutup'
    $closed = PeriodeTutupBuku::where('bulan', $bulan)
        ->where('tahun', $tahun)
        ->where('status', 'tutup')
        ->exists();

    if ($closed) {
        $namaBulan = $date->translatedFormat('F Y');
        throw new \Exception("Periode {$namaBulan} sudah ditutup. Tidak dapat menambah/mengubah transaksi.");
    }
}

⚡ 3.3 Konsistensi Data & Atomisitas Jurnal

  • Transaksi Database: Semua posting jurnal beruntun menggunakan DB::beginTransaction() dan DB::commit() untuk mencegah transaksi tersimpan sebagian (*partial writing*) ketika terjadi kegagalan server di tengah proses.
  • Concurrency Control: Untuk menghindari duplikasi nomor transaksi beruntun (seperti `JU-00001`) ketika banyak user mensubmit transaksi bersamaan, sistem menggunakan metode lockForUpdate() pada database untuk menahan pemrosesan antrean secara sinkron.

Proteksi Terhadap Serangan Web OWASP

Penangkalan SQL Injection, XSS, CSRF, dan serangan File Upload

🛡️ 4.1 SQLi, XSS & CSRF Mitigation

Diimplementasikan langsung pada arsitektur framework Laravel:

  • SQL Injection: Seluruh query dibentuk menggunakan ORM Eloquent yang mem-binding parameter menggunakan PDO secara bawaan.
  • XSS (Cross-Site Scripting): Seluruh variable di render pada layout Blade menggunakan tag escaping {{ $variable }} untuk melumpuhkan payload JavaScript berbahaya.
  • CSRF (Cross-Site Request Forgery): Middleware bawaan memverifikasi kesesuaian token enkripsi session pada seluruh endpoint mutasi (POST/PUT/DELETE).

📁 4.2 Keamanan Unggahan File Transaksi (File Upload Safety)

Ketika pengguna mengunggah foto bukti jurnal atau foto anggota, sistem menerapkan proteksi bertingkat:

  1. Validasi Tipe & Ukuran: Hanya mengizinkan file berjenis gambar (JPEG, PNG, JPG, WEBP) dengan batas ukuran maksimum 5MB.
  2. Renaming Acak: Nama file asli dibuang dan diganti dengan string unik acak (`bukti_jurnal_` + timestamp + `uniqid()`) untuk menghindari serangan *directory traversal* dan overwrite file penting.
  3. Penyimpanan Luar Publik: File disimpan di folder storage terisolasi, yang tautannya ke folder public diatur ketat oleh Nginx agar tidak dapat mengeksekusi script PHP mentah jika ada shell script terselubung.
// Implementasi validasi dan penyimpanan file pada JurnalController.php
$request->validate([
    'foto_bukti' => 'nullable|image|mimes:jpeg,png,jpg,webp|max:5120',
]);

if ($request->hasFile('foto_bukti')) {
    $foto = $request->file('foto_bukti');
    $filename = 'bukti_jurnal_' . time() . '_' . uniqid() . '.' . $foto->getClientOriginalExtension();
    $foto->storeAs('public/bukti_transaksi', $filename);
    $fotoBukti = $filename;
}

Server Hardening & Deployment Security

Konfigurasi keamanan pada level server OS, Nginx, dan Logging Audit

🔒 5.1 Nginx Security Configuration

Untuk menyembunyikan arsitektur internal server dan membatasi manipulasi request dari luar, server Nginx di-hardening dengan konfigurasi keamanan khusus:

# Konfigurasi proteksi header dan blokir file rahasia di Nginx
server {
    listen 443 ssl http2;
    server_name *.v5.simpleakunting.id;

    # Enkripsi & Protokol TLS Aman
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    # Proteksi Header Keamanan Web
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;

    # Batasi ukuran unggahan request payload (Max 20MB)
    client_max_body_size 20M;

    # Blokir akses ke dotfiles (.env, .git, .htaccess)
    location ~ /\.(?!well-known) {
        deny all;
    }
}

📝 5.2 Audit Trail Logging

Setiap perubahan data akuntansi (Create, Update, Delete) serta histori login/logout direkam secara real-time pada sistem audit trail yang andal. Log tidak dapat dimanipulasi dari dashboard aplikasi biasa:

  • Merekam user yang bertindak, deskripsi aksi, nama tabel/model, dan kunci baris data.
  • Menangkap nilai sebelum modifikasi (`old_values`) dan sesudah modifikasi (`new_values`).
  • Mendokumentasikan IP address dan user agent penyerang/pengguna untuk keperluan forensik keamanan.
Lihat Trait LogsActivity.php (Auto-Logger Model) ▼ 
<?php
namespace App\Traits;

use App\Models\AuditTrail;

trait LogsActivity
{
    public static function bootLogsActivity(): void
    {
        static::created(function ($model) {
            AuditTrail::log(
                'created',
                class_basename($model) . ' dibuat: ' . ($model->getKey()),
                $model,
                null,
                $model->getAttributes()
            );
        });

        static::updated(function ($model) {
            $dirty = $model->getDirty();
            if (empty($dirty)) return;

            $original = collect($model->getOriginal())->only(array_keys($dirty))->toArray();

            AuditTrail::log(
                'updated',
                class_basename($model) . ' diubah: ' . ($model->getKey()),
                $model,
                $original,
                $dirty
            );
        });

        static::deleted(function ($model) {
            AuditTrail::log(
                'deleted',
                class_basename($model) . ' dihapus: ' . ($model->getKey()),
                $model,
                $model->getAttributes(),
                null
            );
        });
    }
}
